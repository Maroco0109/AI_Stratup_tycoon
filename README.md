# AI 스타트업 타이쿤 (Chat-Driven Tycoon) – README

> **한 줄 소개**
> 채팅만으로 제품 기획→개발→런칭→위기대응을 진행하는 게임입니다. 한국어에 강한 `yanolja/YanoljaNEXT-EEVE-10.8B`(또는 Instruct 변형)을 **Ollama + GGUF**로 로컬에서 띄우고, **Streamlit**으로 UI를 구성합니다.

---

## 1) 프로젝트 개요

* **목표**: “채팅이 곧 게임” 스타트업 경영 시뮬레이터를 구현합니다. 모델은 EEVE 10.8B 계열을 사용합니다. EEVE는 한국어 어휘를 확장하고 한국어 데이터로 튜닝된, SOLAR-10.7B 기반 한국어 특화 모델입니다.
* **메인 루프(전부 채팅)**:

  * 이벤트 발생을 LLM이 수행 → 플레이어(CEO)는 채팅으로 의사결정
  * 라운드마다 지표(스코어) 요약 → 7일차 종료 후 최종 결과 리포트

---

## 2) 구조(로컬 전용)

```
Streamlit (Python, 로컬 앱)
   ├─ 채팅 UI/상태 패널/지표 카드
   └─ 로컬 HTTP 호출 → Ollama
        └─ EEVE(GGUF) 로드 및 추론
```

* **Streamlit**
* **Ollama**

* **언어/프레임워크**: Python 3.10+, **Streamlit**
* **LLM 서빙(로컬)**: **Ollama** + **GGUF**(EEVE 10.8B / EEVE-Instruct 10.8B 권장)
* **모델**: `yanolja/YanoljaNEXT-EEVE-10.8B` 계열(한국어 어휘 확장·튜닝)

## 0) 점수 시스템(공통)

* 시작 점수: **100점**
* 일차별 증감: 규칙에 정의된 범위 내에서 **LLM이 판단해 가감**
* 점수 범위: 최소 0 ~ 상한 제한 없음(단, Day1 보너스는 항목별 +5, 합계 +10 한도)
* 최종 등급(7일 종료 시):

  * **A**: 80점 이상
  * **B**: 60 ~ 79
  * **C**: 30 ~ 59
  * **D**: 0 ~ 29

## 1) Day 1 — AI/LLM을 활용한 회사/제품 제시

* **사용자 입력**: 간단한 아이디어 1문단
  * 프로젝트 제목
  * 타겟 소비층
  * 위험 요소 처리 방법(개인정보 및 사생활 침해, LLM moderation)

  * 입력 예시
    > “사람들의 일기를 감성분석해서 그날 감정에 맞는 책을 추천하는 웹/앱”
    > - 타겟 소비층: 10대 청소년층, 20~30대 청년층
    > - 위험 요소: 개인 정보(일기) 처리 기능(노트 잠금 등), LLM moderation(openai 기준 검증 과정 도입)
  
* **LLM 아이디어 판정 항목** (두 항목 각각 0~+5, 합계 최대 +10)
  * **창의성**: 차별성, 아이디어 신선도
    * AI/LLM을 적절히 잘 활용한 아이디어인지 검증
  * **실현 가능성**: 구현 난이도, 위험요소 식별
    * 특정 소비층을 잘 겨냥하는지(타겟 소비층이 너무 넓거나 좁지는 않은지)
    * 사용되는 알고리즘/구현 요소가 너무 복잡하지는 않는지
    * 위험 요소 식별
      * 개인정보 및 사생활 침해 방지 여부
      * LLM moderation 방지 여부

* **스코어 반영**: 기본 100점에 **보너스 가산**(최대 +10)

**엔진 출력(JSON 예시)**

```json
{
  "day": 1,
  "delta": +7,
  "score": 107,
  "reason": "창의성 +4, 실현 가능성 +3",
  "llm_summary": "일기 텍스트 감정분석 → 개인화 추천의 연결이 명확함. 데이터 수집/개인정보 이슈는 리스크."
}
```

## 2) Day 2 — 프로젝트 장애 대응

* **이벤트**: LLM이 “버그/운영” 이슈 1개를 제시(예: 업로드 실패, 크래시 등).
* **사용자 입력**: 간단한 대응 방안 1문단
  * 원인 파악
  * 해결 방안
* **스코어 반영**: **−20 ~ −5 ~ +0 ~ +5**

  * **부적절**: **−5 ~ −20** (원인 미파악/안전성 무시/현실성 부족)
  * **부분 적절**: **0**(감점 없음)

**엔진 출력(JSON 예시)**

```json
{
  "day": 2,
  "delta": -8,
  "score": 99,
  "reason": "핵심 원인/모니터링 계획 부재로 미흡",
  "llm_summary": "임시 조치만 제시. 재발 방지책 필요."
}
```

---

## 3) Day 3 — 기능 피드백 10개(함정 2개 포함)

* **이벤트**: LLM이 **피드백 10개** 제시(그중 **함정 2개**: “너무 좋아요/별로예요” 같은 비구체적 후기).
* **사용자 입력**: “어떤 피드백을 어떻게 반영할지” 한 문단(핵심 2~3개만 선택)
* **스코어 반영**:

  * **적절히 선별/대응**: **+0 ~ +5**(가점은 작게)
  * **함정에 리소스 투입**: **−5 ~ −20**

**엔진 출력(JSON 예시)**

```json
{
  "day": 3,
  "delta": +2,
  "score": 101,
  "reason": "구체 피드백 우선, 함정은 무시",
  "llm_summary": "온보딩 이탈/추천 정확도 관련 피드백을 우선 반영함."
}
```

---

## 4) Day 4 — 모델 성능 이슈 대응

* **이벤트**: 성능/품질 관련 문제 1개(지연, 과적합, 편향 등).
* **사용자 입력**: 원인 가설 + 즉시/단기 조치 1문단
* **스코어 반영**: **부적절 시 −5 ~ −20**, 적절 시 소폭 가점 또는 0

**엔진 출력(JSON 예시)**

```json
{
  "day": 4,
  "delta": -5,
  "score": 96,
  "reason": "측정/롤백/알림 체계 부재",
  "llm_summary": "성능 재현/모니터링 계획이 약함."
}
```

---

## 5) Day 5 — 데모 릴리즈 & 후기 10개(함정 2개 포함)

* **이벤트**: 평점과 함께 **후기 10개** 제시(함정 2개: 단순 악플/선플, 숫자로 레이블).
* **사용자 입력**: 전체 후기를 분류해 “무시/분석필요” 처리를 요약 + 영양가 없는 함정 문항 번호
  * 최종 분석
  * 영양가가 적은 피드백

    > * 입력 예시
    >   - 분석: "피드백에 대한 요약 및 대처 방안"
    >   - 영양가가 적은 피드백: 1번, 7번
* **스코어 반영**: **함정 대응 시 −5 ~ −20**, 적절 분류/대응은 소폭 가점 또는 0

**엔진 출력(JSON 예시)**

```json
{
  "day": 5,
  "delta": +1,
  "score": 97,
  "reason": "함정 분리 및 핵심 후기 반영",
  "llm_summary": "추천 근거 노출/오탐 사례 수집을 우선."
}
```

## 6) Day 6 — 투자자 미팅(핵심 4요소)

* **사용자 입력**: **개요/목적/주요 타깃/기대 효과**를 한 문단에 요약
* **스코어 반영**:

  * **타깃·효과 불명확/불일치**: **−5 ~ −20**
  * **명확/현실적**: 소폭 가점 또는 0

**엔진 출력(JSON 예시)**

```json
{
  "day": 6,
  "delta": +3,
  "score": 100,
  "reason": "타깃/성과지표 정의 명확",
  "llm_summary": "초기 타깃을 '국내 20~30대 일기 사용자'로 좁히고, 전환/잔존 가설 제시."
}
```
